# Ежедневный ETL-пайплайн: витрины маркетплейса на Airflow

Пайплайн, который каждую ночь собирает витрины выручки и ABC-анализа SKU:
идемпотентная загрузка, проверки качества между слоями, гейт по свежести
источника, ретраи, SLA и алерты.

```
raw.orders ──► stg.orders_daily ──► mart.daily_revenue ──► bi.revenue_daily (matview)
                                └─► mart.sku_abc
```

## Задачи в DAG

| Задача | Что делает |
|---|---|
| `check_source_freshness` | шлюз: если источник отстал сильнее SLO (180 мин) — запуск падает |
| `staging.load_staging` | перезаливает суточные партиции окна: **delete + insert** |
| `staging.quality_staging` | 6 проверок на загруженном staging, провал → стоп |
| `marts.build_daily_revenue` | витрина выручки по дням (SQL, окно 14 дней) |
| `marts.build_sku_abc` | ABC-классификация SKU через оконные функции |
| `quality_marts` | объём, уникальность, отсутствие пустых значений в витринах |
| `publish_for_bi` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` + `ANALYZE` |

## Ключевые решения (и почему именно так)

- **Идемпотентность через delete-insert, а не append.** Повторный запуск за
  день не задваивает строки — это первое, что ломается в ночных пайплайнах.
- **Lookback-окно 3 дня.** Заказы и возвраты на маркетплейсе дозаписываются
  задним числом, поэтому «вчерашняя» цифра через неделю другая. Витрина
  пересобирается за 14 дней, а не за один день.
- **Гейты качества между слоями.** Пайплайн падает на проверках, а не публикует
  мусор в BI: устаревшая или пустая витрина опаснее её отсутствия.
- **Гейт по свежести падает, а не пропускает.** Тихо пропущенный запуск
  выглядит как успешный.
- **ELT внутри одного хранилища.** `INSERT ... SELECT` работает только когда
  источник и приёмник в одной БД — поэтому raw/stg/mart живут в одном Postgres,
  и данные не перекачиваются через драйвер.
- **Секреты в Variable, не в коде.** Адрес вебхука для алертов читается из
  `Variable.get`, в файле его нет.
- **SQL — отдельные файлы с транзакцией.** Читаемее и не превращается в
  конкатенацию строк; параметры всегда через плейсхолдеры `%s`.

## Тесты

```bash
python run_tests.py        # 43 проверки, из них 31 юнит-тест и 12 статических
```

- `tests/test_common.py` — 31 юнит-тест на чистую логику: окна дат, свежесть,
  проверки качества на настоящих DataFrame, генерация SQL (включая отсечение
  SQL-инъекций в именах таблиц).
- `tests/test_dag_structure.py` — разбор DAG через AST: есть ли расписание,
  отключён ли catchup, настроены ли ретраи/SLA/колбэки, идёт ли delete до insert,
  нет ли захардкоженных секретов, согласованы ли SQL-файлы с DAG.

Логика вынесена в `dags/common/*` и **не импортирует Airflow** — поэтому
тестируется без него. Это же и делает её переиспользуемой в других DAG'ах.

## Запуск стенда

```bash
docker compose up -d          # Postgres с демоданными + Airflow на :8080
```

`docker/init.sql` создаёт схемы, таблицы, материализованное представление
(с уникальным индексом, без которого `REFRESH ... CONCURRENTLY` падает) и
60 000 демо-заказов за 30 дней.

**Честная оговорка:** в окружении, где готовился артефакт, Docker недоступен,
поэтому `docker compose up` не прогонялся. DAG и SQL проверены статически
(12 проверок) и юнит-тестами (31), но живой прогон в Airflow остаётся за вами.

## Что бы улучшил дальше

- Перевести сборку витрин на dbt (Airflow Cosmos) — версионирование моделей,
  тесты и lineage из коробки.
- Партиционировать `mart.daily_revenue` по месяцам: сейчас PK по дню, на объёме
  это станет узким местом.
- Вынести проверки в общий слой ожиданий (Great Expectations / Elementary),
  чтобы они описывались декларативно, а не кодом в таске.
- Добавить бэкфилл-режим с явным окном и ограничением параллелизма.
