# 06 · Разбор отзывов: правила против LLM

Классификатор жалоб из отзывов на маркетплейсах: 8 классов, 1 600 отзывов, объяснимое правило
как нижняя планка и опциональное сравнение с LLM.

**Открыть:** [`report.html`](report.html) — один файл, без интернета.

Результат прогона: **accuracy 87.6%**, **macro-F1 89.8%**, 199 ошибок из 1 600.
Худший класс — `нет_жалобы` (F1 78.8%): правила видят «доставка» в фразе «доставка раньше срока»
и ставят жалобу там, где её нет.

---

## Зачем этот артефакт

Задача из реальной работы с маркетплейсами: тысяча отзывов в неделю, руками не разметить,
а бизнесу нужны причины возвратов по классам. Здесь показано, как это решается **сначала дёшево**,
а не сразу через LLM:

1. **Правила первыми.** Регулярки с весами, окно отрицания, нормализация (эмодзи, ё/е, опечатки).
   Работает офлайн, бесплатно, объяснимо: в отчёте у каждого примера видно, какие фрагменты сработали.
2. **Метрики честные.** Главная цифра — macro-F1, а не accuracy: класс `нет_жалобы` занимает 24%
   выборки, и модель «всё — жалоба» выглядела бы на accuracy прилично.
3. **Границы показаны, а не спрятаны.** Раздел «Живые примеры провалов» — это карта ограничений:
   отрицание, смешанные жалобы (размер + качество в одном отзыве), вежливые формулировки.

## Запуск

```bash
python build.py                 # отчёт по правилам (сеть не нужна)
python build.py --with-llm      # добавить сравнение с LLM, нужен OPENAI_API_KEY
python run_tests.py             # 36 тестов
```

Зависимостей нет: только стандартная библиотека Python.

## Классы жалоб

`размер`, `брак_качество`, `доставка`, `цена`, `упаковка`, `описание_не_соответствует`,
`продавец_поддержка`, `нет_жалобы`.

Распределение намеренно неровное — как в жизни: жалоб на размер (13%) больше, чем на упаковку (7%).

## Как считается качество

| Метрика | Смысл |
|---|---|
| Accuracy | доля верных ответов; на несбалансированных классах обманчива |
| Macro-F1 | среднее F1 по 8 классам без веса на размер — основная цифра |
| Precision | из тех, кому поставили класс X, сколько действительно X |
| Recall | из тех, у кого действительно X, скольким поставили X |

Матрица ошибок в отчёте — не украшение: по ней видно, что `нет_жалобы` путается с `доставка`,
а `размер` — с `описание_не_соответствует` (клиент пишет «не тот размер», имея в виду, что
в карточке указан неверный).

## Честные ограничения

- **Отзывы синтетические.** Шаблоны написаны руками, «истинная» метка — это шаблон, из которого
  собран отзыв. Поэтому 87.6% доказывают покрытие своих же шаблонов, а не качество на реальном
  WB/Ozon. Ценность — в структуре ошибок, а не в абсолютной цифре.
- **LLM не запускался** в этом прогоне: нет ключа. Отчёт прямо пишет это, а не подставляет цифру.
  На синтетике LLM предсказуемо выиграл бы у регулярок, и такой вывод ничего не говорит о продакшене.
- **Нет разметки реальных данных.** Первый шаг в проекте — 300–500 настоящих отзывов, размеченных
  руками, и пересчёт метрик. Без этого шага всё выше — про датасет.

## Что было бы следующим шагом

1. Взять реальные отзывы, разметить 300–500 руками (два разметчика + расчёт согласия).
2. Пересчитать метрики и сравнить структуру ошибок с синтетической — где правила ведут себя хуже.
3. Только после этого — LLM на спорных классах (гибрид: правила отвечают за 70% очевидного,
   модель — за остальное), с оценкой стоимости на 1 000 отзывов.
